# PostgreSQL CREATE INDEX CONCURRENTLY Rollout

**One-line description:** Builds approved PostgreSQL indexes on a live database with `CREATE INDEX CONCURRENTLY` outside a transaction block, from the project's migration tool, with lock and statement timeouts, progress tracking in `pg_stat_progress_create_index`, INVALID index cleanup on failure, and the partitioned-table attach procedure.

**Execution Pattern:** Phase Pipeline

---

## Inputs

- `tuning_scope` (object, required): From `sqlo-baseline-scope`.
- `approved_indexes` (object[], required): From `sqlo-index-write-cost`.
- `migration_tool` (string, required): `django`, `rails`, `alembic`, `flyway`, `liquibase`, `knex`, `prisma`, or `raw_sql`.

---

## Outputs

- `index_migration` (object[]): Per index: the migration file, the exact DDL run, start and end time, the `indisvalid` check result, the drop of any `drop_after_build` index, and the rollback statement.

---

## Phase 1: Write the Migration

### Entry Criteria
- `tuning_scope.db_engine` == `postgresql`.
- `approved_indexes` is not empty.

### Actions
1. `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block. Most migration tools wrap migrations in a transaction. Use the tool's opt-out:

| Tool | How |
|---|---|
| Django | `from django.contrib.postgres.operations import AddIndexConcurrently`; set `atomic = False` on the `Migration` class |
| Rails | `disable_ddl_transaction!` in the migration class and `add_index :orders, [:customer_id, :created_at], algorithm: :concurrently, name: "..."` |
| Alembic | `with op.get_context().autocommit_block(): op.create_index("name", "orders", ["customer_id"], postgresql_concurrently=True)` |
| Liquibase | `runInTransaction="false"` on the changeSet, with a `<sql>` element |
| Knex | `exports.config = { transaction: false };` in the migration file, then `knex.raw('CREATE INDEX CONCURRENTLY ...')` |
| Flyway | the script must run outside a transaction; check the Flyway docs for your version (per-script `executeInTransaction=false` configuration) |
| Prisma | create a migration with `--create-only`, edit the SQL to `CREATE INDEX CONCURRENTLY`, and check Prisma's docs for whether your version runs that file in a transaction |
| raw_sql | run with `psql` with autocommit (the default); never inside `BEGIN` |

2. One index per migration file. A failure in one should not leave others half done.
3. Use an explicit index name and `IF NOT EXISTS` only if the tool's retry behavior needs it (note: `IF NOT EXISTS` skips an existing INVALID index too; see Phase 3).
4. Write the rollback migration: `DROP INDEX CONCURRENTLY IF EXISTS name;` (also outside a transaction).

### Output
Migration files and rollback.

### Quality Gate
- The migration file contains the tool's transaction opt-out from the table.
- The SQL generated by the tool contains `CONCURRENTLY` (check with `python manage.py sqlmigrate app 0042`, `bin/rails db:migrate` output with verbose logging, `alembic upgrade --sql`, or the tool's dry-run).

---

## Phase 2: Run Safely

### Entry Criteria
- Phase 1 complete; user approved the run time.

### Actions
1. Session settings for the migration connection:
```
SET lock_timeout = '<user value>';
SET statement_timeout = 0;            -- a build can take longer than the app default; check the role default with SHOW statement_timeout
SET maintenance_work_mem = '<user value>';
```
   `max_parallel_maintenance_workers` (PostgreSQL 11 and later) allows parallel B-tree builds; record its value.
2. Check for long transactions first. CIC waits for every transaction that could see the table to finish, in two phases:
```
SELECT pid, now() - xact_start AS age, state, left(query,100) FROM pg_stat_activity
WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 10;
```
3. Run the migration. Do not run it through PgBouncer in transaction mode; connect directly or through a session-mode pool.
4. Watch progress (PostgreSQL 12 and later) from another session:
```
SELECT pid, phase, blocks_done, blocks_total, tuples_done, tuples_total, lockers_total, lockers_done, current_locker_pid
FROM pg_stat_progress_create_index;
```
   Phases include `waiting for writers before build`, `building index`, `waiting for writers before validation`, `index validation: scanning table`, `waiting for old snapshots`. A long wait in a `waiting for ...` phase names `current_locker_pid`; that session is the blocker.
5. Partitioned table (CIC on the parent is not supported on most versions): 
   1. `CREATE INDEX name ON ONLY parent (cols);` (creates an invalid parent index, metadata only).
   2. For each partition: `CREATE INDEX CONCURRENTLY name_pN ON partition_N (cols);`
   3. For each partition: `ALTER INDEX name ATTACH PARTITION name_pN;`
   4. The parent index becomes valid when all partitions are attached.

### Output
Index built.

### Quality Gate
- `pg_stat_progress_create_index` readings were recorded at least at start and end.
- The command ran on a direct or session-mode connection (recorded).

---

## Phase 3: Validate, Clean Up, Drop Redundant

### Entry Criteria
- Phase 2 finished, with success or error.

### Actions
1. Check validity: `SELECT indexrelid::regclass, indisvalid, indisready FROM pg_index WHERE indexrelid = 'orders_cust_created_idx'::regclass;`. Must be `t`, `t`.
2. Find any invalid index from failed attempts: `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;`. An INVALID index is still updated on every write but never used for reads. Drop it with `DROP INDEX CONCURRENTLY name;` and rerun Phase 2. Never leave one behind.
3. For a UNIQUE index that failed with duplicate key: find duplicates with `SELECT cols, count(*) FROM t GROUP BY cols HAVING count(*) > 1;`, report to the user, and do not delete data on your own.
4. Confirm the index is used: run the target query's EXPLAIN and check `pg_stat_user_indexes.idx_scan` for the new index increases after traffic.
5. Only after step 4: drop each `drop_after_build` index with `DROP INDEX CONCURRENTLY old_name;`, one at a time, after recording its DDL for rollback (`SELECT pg_get_indexdef('old_name'::regclass);`).

### Output
`index_migration`.

### Quality Gate
- `indisvalid` = `t` for every created index.
- `SELECT count(*) FROM pg_index WHERE NOT indisvalid;` returns 0 for this table.
- Every dropped index has its `pg_get_indexdef` output saved.

## Worked Example

Illustrative only.

Input: approved `CREATE INDEX orders_cust_shipped_created_idx ON orders (customer_id, created_at DESC) WHERE status = 'shipped';`, `migration_tool` = `django`.

Phase 1, `shop/migrations/0042_orders_cust_shipped_idx.py`:
```python
from django.contrib.postgres.operations import AddIndexConcurrently
from django.db import migrations, models

class Migration(migrations.Migration):
    atomic = False
    dependencies = [("shop", "0041_auto")]
    operations = [AddIndexConcurrently("order", models.Index(
        fields=["customer_id", "-created_at"], name="orders_cust_shipped_created_idx",
        condition=models.Q(status="shipped")))]
```
`python manage.py sqlmigrate shop 0042` prints `CREATE INDEX CONCURRENTLY "orders_cust_shipped_created_idx" ON "shop_order" ("customer_id", "created_at" DESC) WHERE "status" = 'shipped';`

Phase 2: progress showed `building index` 61 percent at 4 min, done at 9 min 40 s.

Phase 3: `indisvalid` = t; `idx_scan` rose from 0 to 18,204 in 10 minutes; `orders_customer_idx` dropped concurrently after saving its definition.

## Exit Criteria

DONE when every approved index is valid and used, no INVALID index remains, redundant indexes are dropped with their definitions saved, and rollback statements exist.

---

## Error Handling

| Phase | Failure Mode | Response |
|---|---|---|
| Phase 1 | `CREATE INDEX CONCURRENTLY cannot run inside a transaction block` | **Adjust**: apply the tool's transaction opt-out from the table. |
| Phase 2 | `canceling statement due to lock timeout` | **Retry**: drop the INVALID index left behind, wait for a quieter time, rerun. |
| Phase 2 | Stuck in `waiting for old snapshots` | **Adjust**: identify `current_locker_pid`; ask the user about that long transaction; do not terminate it without approval. |
| Phase 3 | `indisvalid` = f | **Retry**: `DROP INDEX CONCURRENTLY`, fix the cause, rebuild. |
