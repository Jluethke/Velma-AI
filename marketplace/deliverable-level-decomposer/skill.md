# Deliverable Level Decomposer

Decompose the initiative into deliverables: the tangible outputs that prove the initiative is complete.

## Inputs

- `initiative-description`: What the initiative achieves
- `acceptance-criteria`: How you know the initiative is complete

## Outputs

- `deliverable-list`: Every deliverable with its acceptance criterion: the specific, testable condition that proves it is complete
- `deliverable-dependencies`: Which deliverables depend on other deliverables

## Process

1. List every tangible output the initiative produces. Each deliverable is something you can point to and say 'this exists now and it did not before.' Examples: a document, a deployed feature, a trained person, a completed migration.
2. For each deliverable, write the acceptance criterion: the specific, testable condition that proves it is complete. 'The report is done' is not testable. 'The report contains data from Q1-Q4, has been reviewed by the finance team, and is published on the intranet' is testable.
3. Map the dependencies: which deliverables must be complete before others can start?
4. If any deliverable cannot be described with a specific acceptance criterion, it is not understood well enough yet. Break it into smaller parts until each part has a clear criterion.
